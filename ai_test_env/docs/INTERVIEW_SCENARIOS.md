## 一、场景题（5 题）

### 场景 1：API 频繁超时，怎么办？

**问题：** 线上发现 DeepSeek API 频繁 timeout，每次 30 秒超时触发异常，用户等了 30 秒才看到错误。

**分析链路：**

```
用户请求 → API 调用 → 30s 超时 → 报错返回 → 体验极差
                    ↓ 优化后
   2s 超时 → 重试（指数退避） → 降到另一个 Key → 降级响应
```

**解决方案：**

1. **缩短超时**：30s → 5s，不让用户空等
2. **加重试**：d23 RetryEngine，指数退避 + Jitter，最多重试 3 次
3. **Key 轮换**：d5 KeyPoolManager，这个 Key 不行换另一个
4. **熔断**：d24 CircuitBreaker，连续 5 次失败断开 30s
5. **降级**：最后一次失败返回降级响应（"服务繁忙，请稍后重试"）

**话术：** "我会分四层处理。短层（秒级）：缩短超时 + 重试。中层（十秒级）：切换 API Key。长层（分钟级）：熔断器断开。兜底：降级响应。从热到冷逐层递进，不让用户空等。"

### 场景 2：发现模型输出有害内容，怎么追责？

**问题：** 线上用户反馈 AI 输出了歧视性语言。你怎么定位问题？

**分析：**

```
用户 prompt → System Prompt → 模型回复
     ↓            ↓              ↑
 是否有攻击？  角色约束够吗？  安全检查漏了？
```

**排查流程：**

1. **查日志**：拉出那次的 prompt、回复、Token 消耗
2. **再现测试**：用同样 prompt 再跑一遍，看是否复现
3. **攻击检测**：d12 InjectionDetector — 用户是不是在诱导
4. **角色检查**：System Prompt 是否明确"不得输出歧视性内容"
5. **关键词过滤**：d6 QualityChecker 加 forbidden_keywords
6. **改进**：加固 System Prompt + 加禁止词检查 + 线上加后处理过滤

**话术：** "先定位是输入问题（用户诱导）还是输出问题（没拦住）。输入问题加固 System Prompt，输出问题加后处理过滤。两个都要修。"

### 场景 3：老板说"用 AI 评 AI 不准"怎么办？

**问题：** 你用 LLM Judge 做自动评分，老板质疑"你叫 AI 评 AI，能信吗？"

**回答思路：**

1. **承认局限性**："是的，LLM Judge 不是 100% 准确"
2. **说明验证方法**："我们和人工标注做过对比，相关性 0.85+"
3. **定位用途**："自动化评分不是取代人工，是快速发现异常——分数突然跌了 20%，人工再去复审那一条"
4. **不置信区间**："我们只看趋势，不纠结单条的绝对分数"

**话术：** "LLM Judge 不是用来替代人，是替代'没人看'。每周 1000 条回复你不可能全看，但自动评分发现某条只有 2 分，人去看那一条就够了。"

### 场景 4：新模型版本回复风格变了，老用例全挂了

**问题：** 模型从 v1 升级到 v2，同一组 prompt 的回复风格全变了。关键词检查用例全 fail。

**分析：**

```
v1: "Python 是一种编程语言。"           → 包含"编程语言" ✅
v2: "Python 是解释型高级语言。"         → 没有"编程语言" ❌
```

**解决方案：**

1. **区分"关键要点"和"表面关键词"**：必查的核心术语不变（"Python"），次要关键词放宽
2. **更新基线**：跑一次 v2 基线，更新 expected_keywords
3. **分层断言**：语义层（LLM Judge 评分）做软校验，关键词层做硬校验
4. **回归报告**：d14 RegressionSuite 自动生成变更对比，确认是"风格优化"还是"能力衰减"

**话术：** "模型升级后用例全挂是正常的——你测的是'它会怎么说'不是'它知道什么'。我的做法是：知识类用例用硬断言，风格类用例用软断言。模型升级时基线更新 2 天，不是重新测 2 周。"

### 场景 5：线上模型突然"变笨了"，怎么排查是模型问题还是 prompt 问题？

**问题：** 这周用户满意度下降了 20%。怎么定位？

**分析矩阵：**

| 层面 | 可能原因 | 验证方法 |
|------|---------|---------|
| Model | 模型端更新/回滚 | 查 API changelog |
| Prompt | System Prompt 被改 | 查版本记录 |
| 数据 | 用户输入变复杂 | 对比本期 vs 上期输入复杂度 |
| 环境 | Key 被限流 | 检查限流日志 |

**排查流程：**

1. **环境**：查 API Key 有没有被限流（d5 KeyPoolManager 日志）
2. **回复**：抽 50 条当前回复跑 d6 QualityChecker 对比上周基线
3. **prompt**：回滚到一个月的 System Prompt，看分数是否恢复
4. **结论**：如果回复质量普遍下降 → 模型问题。如果只在某些场景下降 → prompt 问题。

**话术：** "先排除环境问题（限流、降级），再看数据问题（用户变了还是模型变了）。最实用的手段：用三周前的 System Prompt 配上今天的模型跑一批用例，如果分数恢复了，就是 prompt 问题；没恢复，就是模型问题。"

### 设计 2：CI/CD 门禁系统

**需求：** PR 合并前自动运行 AI 测试，通过才能合。

**流程：**

```
PR 提交 → GitHub Actions 触发
  │
  ├── smoke tests（3 分钟）
  │     └── 通过率 < 95% → ❌ 阻止合并
  │
  ├── security tests（5 分钟）
  │     └── 任何攻击成功 → ❌ 标记需人工审核
  │
  └── 每日凌晨 full tests（30 分钟）
        └── 生成报告 → 发送到团队群
```

**话术：** "我分了两道门。快速门（smoke+security）3-8 分钟，PR 触发。慢速门（full）30 分钟，每日定时。快速门不通过不能合，慢速门不通过出报告，不阻塞开发。"

### 设计 3：Token 费用监控系统

**需求：** 追踪每天 API 调用量和费用，超过预算预警。

**数据流：**

```
API 调用 → 记录 Token → d26 TokenAuditor
  │                      │
  │              每天汇总 → 费用估算
  │                      │
  │              异常检测 → 突增/突降/持续上涨
  │                      │
  │              预警 → 邮件/群通知
```

**话术：** "每天记录调用量，按模型维度拆分。设了三条预警规则：日费用突增 50%（可能被攻击）、日费用突降 80%（可能 Key 挂了）、连续 3 天上涨（正常用量增长）。预警线=预算×80%，到 80% 提醒，到 100% 强停。"
