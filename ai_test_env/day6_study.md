## 二、前置知识讲解

### 2.1 什么是"质量评估"？为什么需要它？

**一句话定义：** 质量评估是判断 AI 回复是否"好"的过程——API 返回 200 OK 只是起点，回复内容合格才是终点。

**类比：**
```
Day 1-5 在测什么？—— 电线有没有通电（API 连通性）
                    —— 电压稳不稳定（参数边界）
                    —— 插头会不会起火（错误处理）

Day 6 开始测什么？—— 通电后，灯泡亮不亮、亮得对不对
                    —— 内容本身好不好
```

**为什么 Day 6 到 Day 10 比前面的五天更难？**

| 维度 | Day 1-5（API 验证） | Day 6-10（质量评估） |
|:----|:-------------------|:-------------------|
| 预期结果 | 确定的（返回 200 / 返回 400） | 模糊的（回复好不好是主观的） |
| 断言方式 | 等式 / 不等式 | 评分 / 覆盖 / 分类 |
| 环境依赖 | 只依赖 API 在线 | 还需要标准答案集、评判标准 |
| 自动化难度 | 容易 | 中等 |
| 主观因素 | 无 | 有（不同人判断标准不同） |

### 2.2 质量评估的四个层次

```
层次 1：连通性（第 1 周）
  API 能响应吗？状态码 2xx？
  → 验证：smoke_test.py, ok

层次 2：结构完整性（第 1 周）
  响应字段齐全吗？类型对吗？
  → 验证：response_validator.py, ok

层次 3：内容准确性（第 2 周 ← 我们在这里）
  回复内容正确吗？包含了该有的信息吗？
  有没有说了不该说的？
  → 今天的内容

层次 4：语义理解（第 3 周以后）
  回复的意图正确吗？逻辑通顺吗？
  和理想回复的语义相似度有多高？
  → 后续的 LLM-as-Judge 等
```

### 2.3 关键词覆盖检查——最简单但最实用的质检方法

**原理：** 如果 AI 应该提到某些关键信息，就在回复中搜索这些词是否出现。

**适用场景：**
- 客服回复必须包含订单号
- 技术支持回复必须包含产品名
- 翻译必须包含指定术语
- 金融回答不能出现"保本"、"稳赚"等违规词

**局限（面试重点）：**
```
优点                             缺点
────────                       ────────
实现简单，一行代码              只检查"出现"，不检查"在什么语境出现"
零成本，不需要标注数据           "这本书不错" ← 包含"不"（误判）
可解释性强                       "Python 不是 Java" ← 包含"Java"（误判）
适合做第一道防线                测不到"说了但没有说对"的情况
```

**面试话术：**
> "关键词检查是最基础的质检手段，我把它作为第一道防线。它不能发现语义错误——比如 AI 说了'Java 比 Python 快'而你的必含词是'Python'，它会通过。但作为 CI 门禁的第一层、过滤明显不合格的回复，它的性价比极高。更深入的语义检查交给后续的 LLM-as-Judge。"

### 2.4 否定词检测——防止 AI"说错话"

**原理：** 定义一张"红线清单"，回复中一旦出现这些词就判 FAIL。

**典型红线清单：**
| 场景 | 禁止词 |
|:----|:------|
| 医疗 | ["吃药", "诊断", "治疗方案"] |
| 金融 | ["保本", "稳赚", "内部消息"] |
| 竞品 | ["差", "烂", "不好用", "垃圾"] |
| 安全 | ["密码", "验证码", "请提供你的..."] |
| 法律 | ["应该起诉", "胜诉率"] |

### 2.5 综合评分算法——不止是"通过/不通过"

**为什么需要分数而不仅是二值？**

```
二值（PASS/FAIL）的问题：
  回复A：覆盖率 99%，一个词没写到 → FAIL（一刀切）
  回复B：覆盖率 50%，没有违规词 → PASS（太宽松）

分数（0~1.0）的好处：
  回复A：0.99 分，"基本上很好，一个小瑕疵"
  回复B：0.50 分，"质量偏低，需要优化"
```

**本模块的评分公式：**

```
总分 = 关键词覆盖分 × 0.6 + 否定词分 × 0.4

关键词覆盖分 = 出现的关键词数 / 总所需关键词数 × 0.6
  例：需 5 个词，出现 3 个 → 3/5 × 0.6 = 0.36

否定词分：
  没有违规：0.4
  有违规：0.4 × (1 - 违规数/总禁用词数)
  例：有 3 个禁用词，出现了 1 个 → 0.4 × (1 - 1/3) = 0.267

总分 = 0.36 + 0.267 = 0.627
```

**分数含义参考：**
| 分数范围 | 含义 | 动作 |
|:--------|:----|:----|
| 0.90 - 1.00 | 优秀 | 可通过门禁 |
| 0.70 - 0.89 | 良好 | 人工抽查 |
| 0.50 - 0.69 | 一般 | 需要复查 |
| < 0.50 | 差 | 禁止上线 |

## 三、代码设计：质量检查器

### 3.1 模块架构图

```
utils/quality_checker.py
│
├── QualityChecker          ← 主类（对外接口）
│   ├── check()             ← 单次质量检查
│   ├── batch_check()       ← 批量质量检查
│   ├── summary()           ← 统计汇总
│   └── reset()             ← 重置统计
│
├── CheckResult             ← 单次检查结果
│   └── report()            ← 生成可读报告
│
└── BatchReport             ← 批量检查报告
    └── report()            ← 生成汇总报告
```

### 3.2 关键设计决策

| 决策 | 选择 | 理由 |
|:----|:----|:-----|
| 大小写敏感 | **不敏感** | AI 回复大小写不固定，强制区分会导致误报 |
| 部分匹配还是完全匹配 | **子串匹配** | 简单实用，无需分词 |
| 评分权重 | 覆盖 0.6 + 否定 0.4 | 确保覆盖比禁止更重要（说了该说的 > 没说不该说的） |
| 通过条件 | **全部满足** | 关键词必须全部出现且无违规 |

### 3.3 为什么不用更高级的匹配？

```
问：为什么不用 NLP 匹配？比如词向量相似度？
答：性价比问题。

NLP 匹配的代价：
  - 需要加载一个模型（几百 MB 内存）
  - 每次匹配要计算向量（费时间）
  - 配置和维护复杂

关键词匹配的收益：
  - 零额外依赖
  - 执行 < 1ms
  - 可解释性强（"缺失了关键词X" 可以直接反馈给产品经理）

结论：先用关键词匹配做第一道筛子，筛掉的都是"明显不合格"的回复。
高级匹配留给 LLM-as-Judge（Day 9）做更精细的评估。
```

参数设计要点：
- `must_contain` 和 `expected_keywords` 是别名——不管用户叫它什么都行
- `must_not_contain` 和 `forbidden_keywords` 同理
- 返回 `CheckResult` 对象而不是字典——对象可以用 `result.passed`、`result.report()` 等

**内部方法 `_check_keywords()`：**

```python
def _check_keywords(self, response: str, keywords: List[str]) -> Dict:
    if not keywords:
        return {"all_present": True, "details": [], "missing": [], "present": []}

    response_lower = response.lower()
    ...
```

设计要点：
- 空关键词列表默认通过（不要求 = 不需要检查）
- `response.lower()` 大小写归一化——确保 `"PYTHON"` 匹配 `"python"`
- 返回结构包含 `missing`（缺失的）和 `present`（存在的）——报告生成要用

**评分方法 `_compute_score()`：**

```python
def _compute_score(self, inclusion: Dict, exclusion: Dict) -> float:
    required_count = len(inclusion["details"])
    found_count = len(inclusion["present"])
    coverage_score = (found_count / required_count * 0.6) if required_count > 0 else 0.6

    forbidden_count = len(exclusion["details"])
    violations_count = len(exclusion["violations"])
    forbidden_score = (1.0 - violations_count / max(forbidden_count, 1)) * 0.4

    return round(max(0.0, coverage_score + forbidden_score), 2)
```

评分逻辑拆解：
1. 如果不需要关键词 → 覆盖分 0.6（满分）
2. 如果需要 N 个关键词，找到 M 个 → 覆盖分 = M/N × 0.6
3. 如果有 M 个禁用词，违规了 N 个 → 否定分 = (1 - N/M) × 0.4
4. 总分 = 覆盖分 + 否定分

**`CheckResult` 类：**

```python
class CheckResult:
    def report(self) -> str:
        """生成人类可读的报告"""
```

关键设计：`report()` 方法生成格式化的文本报告，用于控制台输出和日志记录。不需要打开文件就能看到检查结果。

**`BatchReport` 类：**

```python
class BatchReport:
    def summary(self) -> Dict:
    def report(self) -> str:
```

支持批量运行后一键生成汇总统计：总数、通过数、通过率、平均分、每个用例的明细。

## 七、面试常见问题与回答

### Q1：关键词覆盖检查有什么局限性？

```
答：主要有四点局限。

第一，只检查"出现/不出现"，不检查"语境"。比如
"Python 不是 Java"包含了"Java"，但我们本意是查
竞品对比是不是提到了竞品名，这里其实是正常讨论。

第二，测不到语义。AI 说了"AI 需要算力和数据"，
但正确答案是"算法、算力、数据三要素"——关键词说
了 2/3 但缺少"算法"，语义上算力+数据也算是对他
意图的回应，但我们的检查会判 FAIL。

第三，发音相同字形不同查不到。"机器学习"和"机器
学习"——其实一样，但子串匹配不认为一样。

第四，需要人工维护关键词列表。业务变了、产品改名
了，关键词列表也得跟着改。

所以关键词检查是"第一道防线"，不是"唯一防线"。
更精细的检查需要 LLM-as-Judge 来做。
```

### Q2：通过率设置多少合适？

```
答：不同的场景通过率应该不同。

如果是一个通用的知识问答系统，我建议通过率设在
85-90%——因为用户问题千变万化，关键词列表不可能
覆盖所有情况。通过率设太高会导致频繁误报。

如果是客服系统处理标准问题（查余额、查订单），
我会把通过率设到 95-98%——因为这类问题答案是标准的。

如果是一个开放式的写作助手，关键词检查本来就不太
适用，我会使用评分（比如 0.7 以上算合格）而不是
二值 PASS/FAIL。

关键原则：不要追求 100% 通过率。100% 通过要么是
关键词太简单/太少，要么是测试用例太弱。一个健康的
质检系统应该有 5-15% 的失败率。
```

### Q3：怎么维护关键词列表？谁来维护？

```
答：关键词维护是质检系统最费力的部分。我建议：

谁维护：产品经理 + 测试工程师共同维护。
  产品经理定义"应该说什么"，测试工程师执行。
  产品经理提供场景的关键词要求（"金融回答必须有
  '风险提示'和'非保本'"），测试工程师写进用例。

怎么维护：
  1. 建立场景-关键词映射表，定期评审
  2. 每次产品功能迭代同步更新关键词
  3. 分析历史 FAIL 用例，把"误报"的关键词删除
  4. 把维护的量降到每个场景 3-8 个关键词

迭代策略：
  上线初期 → 宽松（5 个关键词）
  稳定期 → 收紧（8-10 个关键词）
  成熟期 → 动态调整（通过率波动 < 3%）
```

### Q4：什么是"通过率"和"召回率"？在质检中怎么用？

```
答：这两个概念来自信息检索和信息提取。

通过率 = 检查通过的用例数 / 总用例数 × 100%
  衡量的是"质检系统有多严格"
  通过率低 → 说明多数回复不满足要求

召回率 = 系统发现的问题数 / 实际存在的问题数 × 100%
  衡量的是"质检系统能发现多少问题"
  召回率低 → 有漏网的问题没发现

在质检中的应用：
  通过率是用来监控生产环境的——每天看通过率趋势，
  如果突然下降说明模型或 prompt 出了问题。

  召回率是用来评估质检系统本身的——你人工抽查 100
  条回复，把有问题的标出来，再看质检系统发现了多少。
  如果召回率 < 80%，说明质检规则太弱，需要补充关键词。
```

### Q5：如果必含词有 10 个，其中 1 个没出现就判 FAIL 太严格了，怎么办？

```
答：我会引入权重分级。

关键词不应该"一视同仁"。我会把关键词分为三级：

  必须（必须出现）— 权重 5 分，缺失直接 FAIL
    eg. 客服回复必须包含"订单号"

  重要（尽量出现）— 权重 3 分，缺失扣分不 FAIL
    eg. 技术回复包含版本号

  建议（最好出现）— 权重 1 分，缺失不扣分
    eg. 回复中有礼貌用语

然后按照：总分 = 满足权重和 / 总权重和，设置一个
阈值（如 0.8）来决定 PASS/FAIL。这样即使用户回复
有 10 个要求，缺了一两个不致命的长尾词也不会误判。
```
