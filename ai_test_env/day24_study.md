## 二、三态模型

```
       ┌──────────┐
       │  CLOSED  │ ←── 正常，请求通过
       └────┬─────┘
            │ 连续失败 > 阈值
            ▼
       ┌──────────┐
       │   OPEN   │ ←── 熔断，快速失败
       └────┬─────┘
            │ 超时后
            ▼
       ┌───────────┐
       │ HALF_OPEN │ ←── 试探性放行
       └─────┬─────┘
      ┌──────┴──────┐
      ▼              ▼
   CLOSED          OPEN
  (成功够多)     (失败够多)
```

### 关键参数

| 参数 | 默认值 | 作用 |
|------|--------|------|
| failure_threshold | 5 | 连续几次失败触发熔断 |
| recovery_timeout | 30s | OPEN 到 HALF_OPEN 等待时间 |
| half_open_max_requests | 3 | HALF_OPEN 最大探测数 |
| half_open_success_ratio | 0.5 | 探测成功率阈值 |

## 四、面试话术

**熔断 vs 重试：** "重试解决瞬时故障（5xx/超时），熔断解决持续故障（服务下线/网络断连）。前者是乐观策略，后者是悲观策略。"

**fallback：** "熔断时不能直接抛异常阻塞业务。我用 fallback 返回兜底数据，保证用户体验不中断。"

**HALF_OPEN 设计：** "OPEN 后定期放少量请求探测下游状态。成功率达到 50% 就恢复 CLOSED，否则回到 OPEN。这种设计避免来回抖动。"
